    Skills

    Each skill owns one job and carries its own name and description. The assistant matches on those, so there is no dispatch table to maintain and no per-workflow always-on cost.

    Always-on router

    Only rules that must hold in every conversation: load MCP guidance when tools are involved, never re-read what is already loaded, subagent ground rules, and the no-merge rule.

    On-demand playbook

    Edge cases a description cannot express: two skills overlap, a task spans phases, nothing matches, or a subagent might help. Read only when one of those fires.

    Live replay

    Pick a prompt. The replay shows what loads, what does not, and the workflow the skill will follow. It is pre-computed from tests/skill-triggers.json and the real skill files, so it costs nothing to run again and again.

      Workflow outline
      
      
        
    
        
  
        
  
        
    
        Say when, and when not
        Every skill states what triggers it and what it is not for, and points to the neighbour that owns the near-miss.
        
    
        Rules with reasons
        Instructions are specific and checkable: coverage targets, read the code first, confirm before anything destructive, escalate by a fixed ladder.
        
    
        Edited like code
        Skills are versioned, linted, renamed through a manifest with migration, and refined against a trigger corpus instead of by feel.
        
  
        

        


        
  
        Efficiency: three ways to work with an agent
        
  
        The same task, three ways. Prompting is an agent with no instructions that you correct over and over. Loading instructions is a trained agent that reads every instruction file every time. Routing is a trained agent that reads only the files the request needs.
        
  
        
    
        
    
        
      Illustrative model: change the assumptions
      
        Two things are measured from this repository: how much instruction text each approach puts in front of the agent per turn, and that routing loads one skill while loading-everything loads all of them. The other two inputs are assumptions, because no file in a repository can say how many attempts a task takes or how large a conversation grows. Set them from your own experience, or from a Copilot usage report for a real task.
        
      
        
        
        
        
      
        
      
        
    
        
  
        
  
        What loads, and what doesn't
        
  
        
  
        
    
        Lazy-loaded MCP guidance
        The MCP guidance used to be one 1,027-line file loaded up front. It is now a -line index plus one file per server, read only when that server is used.
        
    
        Three escalation tiers
        Do it inline. For heavy read-only batches, delegate to a cheap in-assistant worker. Hand off to a second agent only when your own budget is the constraint, using a short HANDOFF.md note so nothing is lost.
        
    
        Match the model to the task
        Pattern-following work (reviews, docs, stories) runs on cheaper models; multi-step reasoning is reserved for stronger ones, and each skill says which.
        
  
        

        


        
  
        Guardrails
        
  
        Autonomy with limits. Each rule is written where agents read it, and a test fails when it drifts.
        
  
        

        


        
  
        Engineering rigor
        
  
        The instructions are treated as production code:  test suites,  prompt cases in the demo corpus, and  versioned releases.
